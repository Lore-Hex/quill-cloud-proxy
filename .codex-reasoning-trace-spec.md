# Task: stop discarding reasoning/thinking traces in chat-completions output

Enclave (`enclave-go`). BUILD + TEST ONLY — no commit/push/deploy. Do not
touch `.codex-*` files.

## Bug (publicly reported)

A client comparing TrustedRouter vs OpenRouter found: "the same model's
[reasoning] trace was silently discarded by TrustedRouter's chat translation
and delivered by OpenRouter's." Confirmed:

- NON-STREAMING chat (`internal/adapter/adapter.go` `WriteChatCompletionResponse`,
  ~line 362-415): the assistant `message` is built with only `role` + `content`
  (text). The reassembled extended-thinking blocks (`StreamResult.Thinking`,
  reassembled at ~line 504) are NEVER attached — so a non-streaming
  /chat/completions response drops the reasoning trace entirely. Eval/benchmark
  clients use non-streaming, so they lost Fable's trace.
- STREAMING (~line 592-609): thinking_delta IS emitted, but as
  `reasoning_content` + `thinking` — NOT OpenRouter's field name `reasoning`,
  so clients keying on `reasoning` (the OpenRouter/OpenAI-reasoning convention
  the report compares against) still miss it.

## Fix

### 1. `WriteChatCompletionResponse` — attach reasoning to the message

Add a parameter `reasoning string` (the concatenated reasoning/thinking text,
"" when none). After the `message` map is built, BEFORE returning, when
`reasoning != ""` set BOTH keys (OpenRouter uses `reasoning`; DeepSeek and our
own streaming use `reasoning_content`; emit both for max client compat):
```go
if reasoning != "" {
    message["reasoning"] = reasoning
    message["reasoning_content"] = reasoning
}
```
Attach it independent of content/tool_calls (a tool-only or empty-text turn can
still carry reasoning).

### 2. Thread the reasoning text from every caller

Find every caller of `WriteChatCompletionResponse` (grep). Pass the reasoning
the path has available:
- Anthropic path (the reported case): join `StreamResult.Thinking[i].Text` in
  order into one string (add a small helper e.g. `joinThinking(result.Thinking)`
  next to ThinkingBlock). This is the primary fix.
- OpenAI-compatible path: if the collector already captures upstream
  `reasoning_content`/`reasoning` deltas into a field, pass that; if it is not
  currently captured, pass "" and leave a `// TODO(reasoning passthrough)`
  comment rather than inventing capture in this task.
- Gemini path: same — pass captured `thought` text if available, else "" + TODO.
Do NOT change token accounting; reasoning TEXT and reasoning TOKENS are separate.

### 3. Streaming: add the `reasoning` field name

In the `thinking_delta` case (~line 604) add `"reasoning": deltaText` alongside
the existing `reasoning_content` and `thinking` keys, so streaming clients on
the OpenRouter convention also receive it. If the OpenAI-compatible stream
translation (`internal/llm/stream_translate.go`) passes through upstream
`reasoning_content` deltas, mirror the same both-names emission there (only if
it already handles reasoning deltas — do not add new capture).

## Tests (`internal/adapter`)

1. Non-streaming Anthropic-shaped response that includes thinking blocks →
   `WriteChatCompletionResponse` output's `choices[0].message.reasoning` and
   `.reasoning_content` both equal the joined thinking text; `.content` is the
   answer text.
2. Non-streaming with NO thinking → neither reasoning key is present (no empty-
   string pollution).
3. Streaming thinking_delta → the emitted chunk delta contains `reasoning`,
   `reasoning_content`, and `thinking` all set to the delta text.
4. Reasoning present alongside tool_calls (content nil) → reasoning still on the
   message.
