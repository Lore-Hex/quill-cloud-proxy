# Task: accept `max_completion_tokens` (and `max_output_tokens`) on the chat path

Enclave (`enclave-go`). BUILD + TEST ONLY — do NOT push, do NOT deploy, do NOT
commit. Do not touch `.codex-*` files.

## Bug (confirmed, publicly reported)

`OpenAIChatRequest` (`internal/types/types.go:178-203`) parses only
`max_tokens` (line 186). Modern OpenAI chat clients / SDKs send
`max_completion_tokens` (gpt-5.x REQUIRES it); the Responses/Gemini spelling
is `max_output_tokens`. When a client sends `max_completion_tokens` and NOT
`max_tokens`, `req.MaxTokens` is nil, so:
- `adapter.go:86-88` defaults the Anthropic/Bedrock cap to `DefaultMaxTokens`
  (**4096**) → responses truncated at 4096 (this made Claude Fable 5 look
  broken in a public benchmark).
- `MaxTokensExplicit` is false and the value never reaches the outbound
  builders (`byok.go:334`, `openrouter.go:229`), so OpenAI-compatible
  providers also fall to their own defaults.

The OUTBOUND side is already correct — `byok.go` emits the right per-provider
spelling (`max_completion_tokens` for gpt-5.x, `max_tokens` otherwise). The
fix is purely INBOUND: parse the aliases and canonicalize into `MaxTokens`.

## Fix

### 1. `internal/types/types.go` — `OpenAIChatRequest`

Add two alias fields near line 186:
```go
	MaxTokens           *int `json:"max_tokens,omitempty"`
	MaxCompletionTokens *int `json:"max_completion_tokens,omitempty"`
	MaxOutputTokens     *int `json:"max_output_tokens,omitempty"`
```
Add a method that canonicalizes into `MaxTokens` (first present wins,
deterministic; comment the precedence):
```go
// NormalizeMaxTokens folds the OpenAI-chat (`max_completion_tokens`) and
// Responses/Gemini (`max_output_tokens`) output-limit spellings into the
// canonical MaxTokens so every downstream reader (Anthropic default,
// MaxTokensExplicit, byok/openrouter passthrough) honors a client's cap
// regardless of which name they used. Precedence: max_tokens (legacy/explicit)
// > max_completion_tokens (modern OpenAI chat) > max_output_tokens.
func (r *OpenAIChatRequest) NormalizeMaxTokens() {
	if r.MaxTokens != nil {
		return
	}
	if r.MaxCompletionTokens != nil {
		r.MaxTokens = r.MaxCompletionTokens
		return
	}
	if r.MaxOutputTokens != nil {
		r.MaxTokens = r.MaxOutputTokens
	}
}
```

### 2. Call it at every inbound decode site

Find where `OpenAIChatRequest` is unmarshaled from the client body on the
serving paths (chat/completions; and /messages, /responses if they populate an
OpenAIChatRequest) and call `req.NormalizeMaxTokens()` immediately after a
successful `json.Unmarshal`/decode, BEFORE any routing/adapter/estimate logic
reads `req.MaxTokens`. Grep `OpenAIChatRequest{` and `Unmarshal`/`Decode` in
`cmd/enclave/` and `internal/`. If there is a single shared decode helper,
one call there suffices; otherwise cover each serving handler. Do NOT normalize
inside deep provider builders — do it once at ingest so `MaxTokensExplicit`
(adapter.go) is computed correctly.

## Tests (`internal/types` + `internal/adapter`, and the handler if practical)

1. `max_completion_tokens` only → after NormalizeMaxTokens, `MaxTokens` set to
   that value; the Anthropic adapter (`adapter.go`) uses it (NOT 4096) and
   `MaxTokensExplicit == true`.
2. `max_output_tokens` only → same, folded into MaxTokens.
3. `max_tokens` only → unchanged (precedence).
4. both `max_tokens` and `max_completion_tokens` → `max_tokens` wins
   (deterministic legacy precedence).
5. none → `MaxTokens` stays nil → adapter still applies the 4096 default
   (unchanged; Anthropic requires a value).
6. End-to-end-ish: a decoded chat request with only `max_completion_tokens`
   produces an outbound Anthropic request whose `MaxTokens` equals the client
   value, and (if easy to assert) the OpenAI-compatible passthrough carries it.
